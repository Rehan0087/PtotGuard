# Field Verification Session Design

## Goal

Add a durable, authenticated field-verification session to the accepted Field Agent case workflow without redesigning the existing assigned-visits and capture screens. Starting and completing field work must be server-confirmed, resumable, auditable, and safe under concurrent requests.

## Scope

This change covers the session model, server-side lifecycle enforcement, start/resume/completion APIs, mock parity, existing-screen integration, and automated tests. It does not add GPS functionality, a new dashboard, offline synchronization, reassignment, or administrative controls for failed and cancelled sessions. Existing capture controls remain present, but this chunk does not expand their GPS behavior.

## Existing Model Boundaries

`FieldReport` remains the assigned case and eventual field report. It already links a parcel, optional dispute or mutation, and assigned Field Agent, and it already drives the current UI. Replacing it would create unnecessary contract and UI churn.

A new `FieldSurveySession` represents the time-bounded execution of that assignment. It has a one-to-one relationship with `FieldReport`, because this workflow permits only one field-verification session for an assignment. The linked report supplies the canonical case and parcel relationship; the session also stores the assigned agent and the parcel's ULPIN as the available BhumiID snapshot.

## Data Model

Add a Prisma `FieldSurveySession` model using the project's current string-status and camel-case field conventions:

- `id: String` primary key, generated by the application as `fs-<uuid>`.
- `fieldReportId: String` unique foreign key to `FieldReport`.
- `bhumiId: String?`, copied from `Parcel.ulpin` at start when available.
- `assignedAgentId: String` foreign key to `User`.
- `status: String`, initially `in-progress`.
- `startedAt: DateTime`, recorded by the server.
- `completedAt: DateTime?`, recorded by the server only on completion.

Add back-relations on `FieldReport` and `User`, indexes for agent and status lookup, and a migration that creates the table, unique constraint, indexes, and foreign keys. The unique `fieldReportId` constraint is the database-level duplicate-session safeguard.

The shared domain package exposes `FieldSurveyStatus` and `FieldSurveySession`. The explicit lifecycle is:

- No session row: `not-started`, derived from an accepted case with no session.
- `in-progress` to `completed`.
- `in-progress` to `failed`.
- `in-progress` to `cancelled`.
- All other transitions are invalid.

Only `in-progress` and `completed` are exposed as Field Agent actions in this chunk. `failed` and `cancelled` are modeled so future administrative flows cannot invent incompatible state values.

## Case Workflow and Synchronization

The server owns all transitions. Existing lowercase values remain the storage and API convention.

| Business stage | Stored state |
| --- | --- |
| ASSIGNED | `FieldReport.status = assigned` |
| ACCEPTED | `FieldReport.status = accepted` |
| Optional travel marker | `FieldReport.status = en-route` |
| IN_PROGRESS / FIELD CAPTURE | `FieldReport.status = in-progress`, session `in-progress` |
| FIELD_CAPTURE_COMPLETE | `FieldReport.status = completed`, session `completed` |
| UNDER_REVIEW | Linked `Dispute.status = under-review` |

Starting is allowed from `accepted` or the existing optional `en-route` state. A generic report patch may still move `accepted` to `en-route`, but it may not enter `in-progress` or `completed`; those transitions belong to the dedicated session endpoints. Assigned cases must be accepted first.

Completion is allowed only when the report and its owned session are both `in-progress` and the existing `filingReview` evidence-and-notes gate passes. It atomically marks the session `completed`, sets `completedAt`, marks the report `completed`, sets `submittedAt`, and moves a linked dispute from `field-visit-scheduled` to `under-review`. A dispute that has independently moved elsewhere is not forced backward.

## API Contract

### Start

`POST /field-reports/:id/survey/start`

- Requires a valid access token and `field-agent` role.
- Resolves the authenticated user from the token.
- Returns `404` when the report does not exist or belongs to another agent, avoiding ownership disclosure.
- Returns `409` when the case state changed, the report is not accepted or en route, or a session already exists.
- In one transaction, conditionally claims the current report state, loads the parcel's ULPIN, creates the session, and appends a `field-survey/start` audit event.
- Returns `{ report, survey }` only after the transaction commits.

The conditional report update and unique session constraint jointly protect against duplicate concurrent starts.

### Resume and Detail

`GET /field-reports/:id` keeps its existing authorization and returns:

```ts
{
  report: FieldReport;
  parcel: Parcel | null;
  survey: FieldSurveySession | null;
}
```

Returning the stored session lets the existing page restore an active state after navigation or refresh without calling start again.

### Complete

`POST /field-reports/:id/survey/complete`

Request body:

```ts
{ notes: string }
```

- Requires the same authentication, role, and ownership checks as start.
- Returns `409` if no session exists, either record is not `in-progress`, or a concurrent request has already changed them.
- Returns `422` with the existing validation contract if required evidence or findings are missing.
- Completes session and report, synchronizes a linked dispute, writes its timeline event, and appends a completion audit event in one transaction.
- Returns `{ report, survey }` after commit.

The generic `PATCH /field-reports/:id` remains available for notes and the optional `accepted` to `en-route` marker, but rejects session-owned transitions.

## Existing UI Integration

No route, dashboard, card structure, layout, color, or component hierarchy is redesigned.

- The current capture-page `Mark on site` action calls the start endpoint.
- It remains disabled while the request is pending and reports success only from the mutation's success callback.
- A returned active session hides the start action and leaves the existing capture interface active.
- Refreshing or revisiting reads the same session through the detail query.
- The current report badge continues to show case status; the existing metadata area shows the session status and server timestamps using existing typography.
- The existing file-report action calls the completion endpoint instead of changing report status through the generic patch.
- Query invalidation refreshes report detail, assigned visits, field-report lists, and linked disputes.

The assigned-visits grid continues using report state as its active indicator, so `in-progress` cases remain visibly active without a new UI construct.

## Mock Backend Parity

The MSW database gains a `fieldSurveySessions` collection. Mock start, detail, and complete handlers implement the same ownership checks, status rules, response shapes, timestamps, duplicate prevention, audit writes, and report/dispute synchronization as the Nest backend. This keeps the documented frontend-first mode behaviorally aligned with the real API.

## Error Handling

- `401`: missing or invalid authentication.
- `403`: authenticated user lacks the Field Agent role.
- `404`: report is missing or assigned to another agent.
- `409`: duplicate start, stale/concurrent update, invalid case/session state, or completion without a started session.
- `422`: filing evidence or findings validation fails.

The frontend keeps existing destructive alerts and toast styling. It does not optimistically claim a start or completion before the server response.

## Testing Strategy

Development follows red-green-refactor.

Shared rule tests cover allowed and rejected survey transitions, including terminal states. Nest contract tests cover authenticated creation, generated start timestamp, BhumiID propagation, audit payload, resume detail, other-agent denial, invalid report states, duplicate and concurrent starts, completion without start, successful completion, and report/dispute synchronization. Existing acceptance tests remain passing.

Mock tests or extracted pure handler-state tests cover equivalent creation, resume, duplication, and synchronization behavior. Frontend behavior is verified through type checking/build plus a rendered browser check in mock mode, confirming the existing page layout remains intact and a started session survives navigation or refresh.

## Acceptance Criteria

- An authenticated assigned agent can start an accepted case and receives the persisted active session.
- Another agent cannot discover or start the session.
- A report can have at most one session, including under concurrent start requests.
- An invalid case or session transition is rejected server-side.
- An active session is returned on detail and restored by the existing capture page.
- Completion cannot occur before start.
- Completion synchronizes session, report, linked dispute, timestamps, timeline, and audit records atomically.
- The current UI structure and styling remain unchanged.
- No new GPS capability is implemented.
